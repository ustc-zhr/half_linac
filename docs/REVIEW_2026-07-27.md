# half_linac 完整审查报告

- 审查日期：2026-07-27
- 审查对象：`half_linac` 当前工作区
- 审查场景：VM / offline、IRFEL 在线装置、应用独立启动与 Control Room 启动
- 审查方式：架构与代码静态审查、机器配置契约检查、现有自动化检查

## 1. 结论摘要

`half_linac` 已经具备较清晰的平台化方向：机器配置、逻辑通道、VM/real
后端、应用级写入策略、统一启动器、运行归档和两套 GUI 主题都已经形成。
这些设计使 HALF 与 IRFEL 能够共享大部分应用逻辑，VM 场景也有较完整的
配置验证基础。

当前结论是：

- VM / offline：基本可用，适合作为开发、算法验证和操作流程演练环境。
- 在线只读监视：在 PV 契约正确且连接稳定的前提下，可继续现场验证。
- 在线写入：具备部分 commissioning 能力，但目前不应无条件视为生产级控制软件。
- 生产上线前必须关闭本报告全部 P0，并完成 P1 中的故障注入、恢复验证和
  GUI 全矩阵检查。

最重要的问题不是算法本身，而是“界面显示的安全状态、配置授权和实际写入”
尚未形成同一个强制闭环。当前工作区中，IRFEL 色散校正同时配置了
`real_status: write_blocked` 和 `write_control.real: allowed`；应用依据后者构造
`write_enabled` EPICS 后端，因此存在状态显示为阻止、实际仍允许写入的冲突。

## 2. 总体评价

| 维度 | 评价 | 结论 |
| --- | --- | --- |
| 简洁且有效 | 基本符合 | machine profile 和共享解析减少了重复，但在线写入、进程管理和 GUI 状态仍存在多套实现 |
| 在线装置安全 | 有明显缺口 | 已有写入策略和部分安全检查，但默认模式、commissioning 门禁、写入确认和恢复报警未形成平台级强制 |
| 功能完整性 | 基本完整 | 主要诊断、校正、扫描和 VM 工作流存在；Energy Feedback、VM 数据同步按钮等仍未完成 |
| 逻辑一致性 | 中等 | VM/real 抽象合理，但 `real_status` 与 `write_control` 可互相矛盾，部分应用绕过统一写入语义 |
| GUI 一致性 | 中上 | 新界面已有统一 header、状态条和主题；旧界面、VM、外部集成和错误呈现仍不一致 |
| 易用性 | 中上 | 主流程可发现，运行状态逐步统一；实机动作的目标、读回、失败恢复和审计反馈仍不足 |
| 测试与可维护性 | 中等 | 现有 pytest 数量可观且本次通过；默认检查仍不运行 pytest，GUI smoke 和 EPICS 故障矩阵不完整 |

## 3. 优先级定义

- **P0**：可能导致实机误写、恢复失败不被发现或安全状态与实际行为不一致。
  进入常规在线写入前必须完成。
- **P1**：可能导致运行状态错误、功能退化或在线故障定位困难。应在下一轮
  commissioning 前完成。
- **P2**：主要影响一致性、可维护性和长期使用效率，可在 P0/P1 稳定后推进。

## 4. P0：上线前必须修改

### P0-1 统一 `real_status` 与实际写入授权

**证据**

- `configs/machines/irfel/apps/dispersion_correction.json:105-108`：
  `real_status` 为 `write_blocked`，但 `write_control.real` 为 `allowed`。
- `src/apps/dispersion_correction/profile_runtime.py:87-93`：
  非 model-only 且 `workflow_writes_allowed()` 为真时，后端直接成为
  `write_enabled`。
- `src/apps/dispersion_correction/gui/main_window.py:5244-5253`：
  操作可用性同样只依据 backend mode 和 `write_control`，未依据
  commissioning 状态。
- `src/shared/machine_profile/write_control.py:23-28`：
  未配置写入策略时默认是 `allowed`。

**影响**

操作员可能看到 “WRITE BLOCKED”，但实机写入路径实际可用。这比单纯的 UI
文案错误更危险，因为安全认知与程序行为相反。

**建议**

1. 立即把 IRFEL 色散校正的状态与策略改成同一结果；在未完成现场验收前应
   fail closed。
2. 为配置验证增加不变量：`not_supported`、`read_only`、`write_blocked`
   不能与 real 写入 `allowed` 同时出现。
3. 把 `real_status` 纳入共享 write authorizer，而不是仅在 launcher 展示。
4. real 模式未声明策略时默认 `blocked`；只有显式配置和验收状态同时满足时
   才允许写。
5. 为该冲突增加回归测试，要求 launcher、独立启动和 CLI 三条路径结论一致。

### P0-2 所有实机写入必须成为可验证事务

**证据**

- `src/apps/bba/main.py:2610-2612` 的 `_safe_put()` 只调用 `pv.put(value)`，
  不等待、不检查返回值、不验证读回。
- BBA 在 `src/apps/bba/main.py:2915-2917`、
  `3174-3175`、`3252-3253` 的 `finally` 中恢复初值，但恢复仍使用同一
  未验证写入；失败可能被静默忽略。
- `src/apps/emit_measure/main.py:3210-3212` 的恢复和 `3230-3237` 的扫描写入
  直接使用 `epics.caput()`；`3376-3379` 虽然保证调用恢复，却不确认恢复成功。
- `src/apps/energy_spectrum/esa_auto_tuner.py:194-210` 的扫描和恢复均直接
  `caput()`，等待的是固定 settle time，不是执行完成或读回到位。
- `src/apps/energy_spectrum/main.py:3781-3794` 对能量设定值做了配置范围检查，
  但写入本身没有完成确认和读回确认。

**影响**

CA 超时、IOC 重启、网络抖动、设备拒绝写入或读回不跟随时，程序仍可能继续
扫描并显示成功。更严重的是，停止或异常后的“恢复初值”可能没有真正完成，
磁铁会停留在扫描末值。

**建议**

建立共享的 `OnlineWriteService` 或等价接口，并逐步替换应用内直接
`caput/PV.put`。一次写入至少包含：

1. 实机模式、commissioning、workflow policy 和 operator arm 校验。
2. PV 连接、权限、数值有限性、软限位和建议变化率校验。
3. `wait=True`、明确 timeout、返回值检查。
4. 指定 readback PV、容差、稳定时间和超时。
5. 失败时进入 `FAULT/HOLD`，禁用后续写入，并显示目标、读回和原因。
6. 扫描保存初值快照；取消、异常和关闭时恢复并验证。
7. 恢复失败必须升级为高优先级报警，不得只 `print()` 或被 `finally` 吞掉。
8. 记录时间、用户/会话、机器、PV、旧值、目标、读回、结果和恢复结果。

现有较好的参考是：

- `src/apps/hv_feedback/epics_client.py:66-72`：等待写完成并检查返回值。
- `src/apps/hv_feedback/safety.py:48-80`：写前验证 PV、读回偏差和绝对限位。
- `src/apps/hv_feedback/runtime.py:123-159`：写前/写后安全检查，失败进入 HOLD。
- `src/apps/dispersion_correction/machine/epics.py:388-419`：写入结果检查和
  读回容差等待。
- `src/apps/solenoid_centering/scan.py:595`、`orbit_correct/correct.py:335-349`：
  已使用带 timeout 的等待式写入，可作为迁移起点。

### P0-3 实机模式必须显式进入，独立启动也要受门禁约束

**证据**

- `configs/machines/irfel/machine.json:7` 把默认模式设为 `real`；
  HALF 的默认模式则是 `configs/machines/half/machine.json:7` 的 `vm`。
- `src/shared/machine_profile/loader.py:140-146` 在未显式指定 backend 时使用
  machine default。
- `src/shared/machine_profile/loader.py:695` 起的基本应用支持校验主要检查
  元素和 workflow 能否解析，不强制 real commissioning 状态。
- `src/apps/launcher/main.py:1035-1043` 的 commissioning 校验主要用于 IRFEL
  real 按钮状态；直接启动应用可以绕过 launcher。
- HALF `energy_spectrum` 当前配置 `write_control.real: allowed`，但非 IRFEL
  commissioning 契约未形成同等强制。

**影响**

选择 IRFEL 或直接启动某个应用时，程序可能默认落入 real。安全边界依赖
启动入口和 UI 控件，而不是由所有写入共享的底层规则强制执行。

**建议**

1. 默认进入 VM；没有 VM 的应用进入 real read-only，而不是 write-enabled。
2. real 写入应经过显式、短时有效的 session arming；界面持续显示
   `MACHINE / BACKEND / ACCESS / CONNECTION`。
3. `load_app_context()` 和共享写入服务都必须检查 commissioning，不允许应用
   通过独立入口绕过。
4. `write_smoke_passed` 只允许受限 commissioning，不等同于
   `commissioned`。
5. launcher 不是安全边界，只是安全状态的一个展示入口。

## 5. P1：下一轮 commissioning 前修改

### P1-1 补齐低风险写入的结果与范围检查

- `src/apps/beam_monitor/main.py:1557-1573` 的曝光时间写入没有配置范围、
  返回值或读回验证；输入错误只输出到终端。
- `src/apps/beam_monitor/main.py:1751-1757` 发布拟合 sigma 时不检查
  `caput_many` 结果，也未区分“诊断发布失败”和“图像读取失败”。
- `src/apps/energy_spectrum/main.py:3241-3257` 的曝光时间写入存在相同问题。

建议复用 P0-2 的共享写入接口。诊断派生量写入应独立标记发布状态，避免把
整个 PV 连接状态误判为不可用。

### P1-2 VM 需要可观察的 READY / STALE / FAULT 状态

**证据**

- `src/virtual_machine/common/start_VM.py:35` 使用 2 秒轮询 JSON 修改时间。
- `src/virtual_machine/common/start_VM.py:170-182` 刷新失败后只打印错误并继续；
  没有发布 fault/stale 状态，也没有冻结或撤销旧数据。
- `src/virtual_machine/common/mainVM.py:482-490` 仍显示 `sim2real` 和
  `real2sim` 占位按钮，tooltip 明确说明未实现。

**建议**

- 发布 VM runtime heartbeat、最后成功更新时间、输入 JSON revision、elegant
  return code 和各类数据发布结果。
- 刷新失败后显式进入 STALE/FAULT，GUI 不再把“进程存活”解释为“数据有效”。
- ready 条件应包含 softIOC CA 可连接、第一次 elegant 成功和关键 PV 已更新。
- 移除或禁用未实现按钮；不要让占位动作出现在正常操作路径。
- Control Room 与 VM GUI 共用进程状态和生命周期管理，减少两套判断逻辑。

### P1-3 测试必须覆盖在线故障，而不仅是正常路径

**现状**

- `scripts/check.sh:8-23` 执行 compileall、shell 语法、machine profile 和
  IRFEL VM acceptance，但不执行 pytest。
- `environment.yml:31` 声明 `pytest>=8`；项目 Conda 环境提供
  Python 3.11.5、pytest 9.0.3 和 Qt offscreen plugin。
- 从仓库根直接运行 pytest 会因为父目录未进入 `PYTHONPATH` 而在收集阶段
  出现 15 个 `No module named 'half_linac'`；执行
  `source scripts/setup.sh` 后主套件为 485 PASS、11 SKIP。
- 11 个 SKIP 都来自 `tests/test_solenoid_centering_gui.py:36-39`：
  测试只有在启动进程前设置 `QT_QPA_PLATFORM=offscreen` 时才运行。再显式选择
  IRFEL/real 和本机 CA 后，该文件 12 项全部通过。
- `scripts/smoke_gui_layouts.py:36-110` 覆盖 launcher、beam monitor、
  energy spectrum、orbit display、CT、orbit correct、BBA、emit measure 和
  HV feedback；未覆盖 solenoid centering、dispersion correction、
  jitter analysis、VM GUI、GOTAcc 和 energy feedback。
- 现有 13 个 GUI smoke 中 12 个通过。HV Feedback 在
  `scripts/smoke_gui_layouts.py:453` 失败，因为同一函数在 `:255` 再次
  `import time`，导致 `time` 成为未赋值的局部变量；这是测试脚本缺陷，不是
  HV Feedback 窗口构造失败。
- Beam Monitor 和 Emit Measure smoke 在构造窗口时仍会初始化 EPICS CA；
  在限制 socket 的沙箱中失败，在允许本机 CA socket 后通过。smoke 应通过
  mock 完全隔离 CA，才能稳定用于 CI。
- 现有 GUI smoke 主要检查控件结构和状态，不等同于截图、字体溢出、窄窗口和
  完整操作流程检查。

**建议测试矩阵**

- 每个 real 写入：授权拒绝、PV 断连、timeout、返回失败、读回不跟随、超限。
- 扫描类应用：开始前快照、运行中取消、关闭窗口、异常、恢复失败。
- BBA / emit / ESA：确认后续扫描点不会在前一写入失败时继续执行。
- VM：JSON 损坏、elegant 失败、输出缺失、发布部分失败、数据 stale。
- GUI：全部入口的 offscreen smoke，加 1280×720、1920×1080 和窄窗口截图；
  检查文本溢出、按钮遮挡、主题切换、运行中锁定和 fault 恢复。
- CI 的必过项应包含 pytest；依赖不足必须失败并给出环境修复提示，不能默默
  退化为只做 compileall。
- 让 pytest 从仓库根可直接运行，避免依赖人工 `PYTHONPATH`；可选择 editable
  install、pytest 配置或统一测试包装脚本。

### P1-4 softIOC/VM 契约不能把“未覆盖”记为 PASS

`src/shared/machine_profile/validation.py:173-208` 对 HALF 的未覆盖 VM PV
判为 FAIL，但对其他机器的 legacy/non-softIOC mapping 仍返回 PASS。本次
IRFEL 检查显示 22 个 mapping 未被 softIOC generator 强制覆盖。

建议把结果区分为：

- managed：必须由 substitutions 生成并完整验证；
- external/legacy：显式声明 owner、来源和可用性检查；
- unknown：FAIL。

至少应把当前 IRFEL 结果标为 WARN，而不是 PASS，并逐项决定迁移或保留。

### P1-5 未完成入口和支持矩阵要与产品状态一致

- `src/apps/launcher/main.py:725-734` 的 Energy Feedback 是 reserved，入口存在
  但未连接。
- HALF 没有 HV Feedback workflow，检查中会 skip。
- Solenoid Centering 是 real-only；HALF 当前又阻止 real 写入，因此它在 HALF
  配置下没有可执行扫描路径。
- VM GUI 的 `sim2real/real2sim` 尚未实现。

建议对未完成能力采取“隐藏或明确禁用”，不要占用主操作界面。发布说明应有
机器/后端/读写状态矩阵，避免“有按钮”被理解为“已验收”。

## 6. P2：一致性和可维护性改进

### P2-1 统一 GUI 基础组件

`docs/gui_style.md` 已经定义 header、status strip、主题 token、状态色和按钮
角色。建议把以下内容固化为共享组件，而不是各应用复制：

- `RuntimeContextWidget`
- `StatusStrip`
- connection / access / fault 状态模型
- real 写入确认对话框
- 可折叠日志
- 主题切换和图表 token
- 后台任务的 start / stop / abort / close 生命周期

老应用如 Orbit Correct、Emit Measure 和 VM 应逐步迁移。Jitter Analysis 与
GOTAcc 属于外部集成，优先在 launcher/wrapper 层统一 runtime context 和状态，
避免大改 vendored 内部代码。

### P2-2 统一错误反馈

当前仍有较多 `print()` 用于输入错误、PV 异常和扫描状态。建议规定：

- 可恢复输入错误：控件附近提示或 warning dialog；
- 连接问题：状态条持续显示；
- 扫描 fault / 恢复失败：不可忽略的 fault banner；
- 详细堆栈：日志面板；
- 每次在线运行：结构化归档。

操作员不应依赖启动终端才能知道一次写入是否成功。

### P2-3 收敛配置和兼容路径

继续按 machine-native element `kind` 和逻辑通道动态派生应用对象，避免在每个
workflow 重复设备列表。保留 workflow 配置给图像几何、扫描默认值、限制和
推荐默认设备等无法可靠推断的少量事实。

对 legacy 配置解析应给出迁移期限和告警，避免新旧 schema 长期双轨。

### P2-4 明确源码、生成物和运行产物边界

仓库已在 `AGENTS.md` 中列出 substitutions、runtime JSON、lattice 和 elegant
输出的生成关系。建议进一步：

- 由单一命令生成并校验派生文件；
- 在运行归档中记录源配置 revision；
- CI 检查误提交的日志、缓存、daily output；
- GUI 清楚显示当前使用的是 bootstrap、latest 还是 archived 数据。

## 7. 功能和逻辑审查

| 子系统 | 当前状态 | 主要结论 |
| --- | --- | --- |
| Control Room | 可用 | 统一入口和支持检查清晰；不能作为唯一实机安全边界 |
| Machine Profile | 方向合理 | 动态元素和逻辑通道有效；commissioning 与 write policy 需要合并约束 |
| Orbit Display | 只读路径合理 | 应继续保持只读和连接状态可见 |
| Orbit Correct | 主要能力存在 | 已有等待式写入；需纳入统一事务、审计和全故障矩阵 |
| Beam Monitor | 主要能力存在 | 图像与拟合流程完整；曝光和 sigma 发布缺少写入闭环 |
| Energy Spectrum | 功能较完整 | 图像、拟合、设定和 auto tune 均存在；实机执行确认与恢复验证不足 |
| BBA | 算法与扫描完整 | 实机扫描和恢复是当前最高风险路径之一 |
| Emit Measure | 扫描、拟合、归档较完整 | 四极铁写入和恢复未验证 |
| CT Monitor | 只读 | 职责简单明确，符合“简洁且有效” |
| Solenoid Centering | IRFEL commissioning 中 | 写入实现相对完整；HALF 配置没有可执行路径 |
| Dispersion Correction | 功能丰富 | 写入适配层较严谨，但当前授权配置自相矛盾 |
| HV Feedback | IRFEL 已标 commissioned | 安全检查、HOLD 和写入等待可作为其他应用参考 |
| Jitter Analysis | 独立集成 | 功能和测试较多；尚未完全进入统一 profile/runtime/GUI 验证矩阵 |
| GOTAcc Optimization | vendored 集成 | 优先改 wrapper 和 launcher，不建议在此轮大改内部 |
| Energy Feedback | 未完成 | launcher 已明确 reserved，应从主操作路径降权或隐藏 |
| VM / softIOC | 基础链路完整 | 配置契约较强，但 runtime 有效性和 stale/fault 表达不足 |

### 逻辑完整性结论

主流程多数具备“选择设备 -> 配置 -> 执行 -> 展示/归档”的闭环，算法层面未发现
需要推翻重做的架构问题。主要逻辑缺口集中在跨应用的非功能契约：

- 谁可以写；
- 当前是否真的处于 real；
- 写入是否完成；
- 设备是否到位；
- 中止后是否恢复；
- 数据是否仍然新鲜；
- 失败是否被操作员明确看到。

这些契约应由共享运行层强制，而不是继续分散在每个 GUI 中。

## 8. GUI 一致性和易用性审查

### 做得较好的部分

- 新 GUI 普遍采用 summary/header、状态条、主工作区和可选日志结构。
- dark/light 主题方向明确，状态色语义基本一致。
- RuntimeContext 逐步显示机器、backend 和模型信息。
- 扫描类应用多数提供 Start/Stop、进度和结果区。
- GUI style guide 明确要求风险不能只靠颜色表达，方向正确。

### 需要改进的部分

1. 旧应用、VM、Jitter 和 GOTAcc 的 header、状态条、按钮角色及文案不完全一致。
2. 部分错误只输出终端，操作员在桌面启动时不易发现。
3. real 危险动作尚未统一显示 `current -> target`、limit、readback 和最终结果。
4. “运行中”“停止中”“恢复中”“恢复失败”没有统一状态机和按钮锁定规则。
5. 未实现按钮和 reserved 入口增加认知负担，不符合“简洁且有效”。
6. 现有 smoke 并未证明实际字体、分辨率和窄窗口没有遮挡。

### 建议的统一在线操作流程

1. 顶部持续显示机器、backend、access、connection。
2. 操作员完成 preflight，界面列出将写入的设备、范围和初值。
3. 显式 arm 后才启用主动作；arm 有超时且切换机器/backend 后立即失效。
4. 执行期间锁定冲突控件，Stop 始终可见。
5. Stop 后先显示 RESTORING，验证完成后才显示 STOPPED。
6. 恢复失败显示 FAULT，给出设备、目标、读回和人工处置提示。

## 9. “简洁且有效”专项结论

当前架构层面基本符合“简洁且有效”，产品层面尚未完全达到。

符合之处：

- 机器差异主要进入 profile，而非复制整套应用。
- 设备选择逐步按 element `kind` 和逻辑通道推导。
- launcher 提供统一入口，VM 和 real 共用主要业务界面。
- CT Monitor 等单一职责应用保持了较低复杂度。

不符合之处：

- 同一安全事实拆成 `real_status`、`write_control`、launcher enable state 和
  app-local 判断，多套状态反而降低有效性。
- 多个应用各自实现 PV 写入、恢复、状态和进程生命周期。
- 未实现按钮、reserved 入口和新旧 GUI 双轨增加无效结构。
- 配置验证把部分“未覆盖”记为 PASS，输出简洁但结论不够有效。

改进原则应是减少状态源和写入实现数量，同时保留清晰的安全反馈、可发现性和
完整操作能力，而不是简单删除必要的检查。

## 11. 在线上线准入条件

以下条件全部满足后，才建议把某个应用标记为 `commissioned`：

- machine profile、real status 和 write policy 无冲突；
- 所有 real 写入都经过共享授权、限位、等待和结果检查；
- 关键执行器有读回容差和 timeout；
- cancel、异常、窗口关闭和进程退出均验证恢复；
- 恢复失败会进入不可忽略的 FAULT；
- PV 断连、IOC 重启、超时和读回卡死测试通过；
- GUI 显示机器、backend、access、connection 和运行状态；
- 在线运行有结构化审计记录；
- 在专用 machine-development 时段完成现场 dry-run 和值班人员签字；
- launcher 与独立启动行为一致。

## 13. 最终建议

保持现有 machine-profile 平台方向，不需要大规模重写。下一阶段应集中做三件事：

1. 把 commissioning、write policy 和实际写入授权合并为一个 fail-closed 契约。
2. 把所有实机写入与恢复迁移到统一、可验证、可审计的事务接口。
3. 用故障注入和完整 GUI 矩阵证明在线异常时系统会停止、报警并可靠恢复。

完成上述工作后，软件可以在不明显增加界面复杂度的前提下，同时提高安全性、
逻辑一致性和操作效率，真正达到“简洁且有效”。
